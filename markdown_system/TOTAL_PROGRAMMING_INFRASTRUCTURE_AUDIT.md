## 4. Hallazgos que condicionan producción, no el bootstrap

1. La política de selección ya es stack-neutral: el roadmap compara Go/JVM/Rust y limita TypeScript al adapter web. Deben eliminarse frases embebidas que todavía lo llaman “núcleo único”, “starter” o “golden”.
2. ~~Los 64 bloques web registraban `golden_starter` como fuente activa.~~ Cerrado en V5: todos declaran el Markdown canónico; el linaje anterior queda sólo en evidencia histórica.
3. Los architecture packs existentes son `CANDIDATE_PACK`; ninguno puede presentarse como sistema completo inmediatamente incorporable.
4. Go cubre backend, outbox/inbox/jobs, autorización por organización y los slices empresariales del blueprint de electromovilidad; todavía faltan adapters externos seleccionados e infraestructura productiva.
5. Mobile/desktop, data/analytics, IA productiva e IaC no se materializan si el blueprint no los requiere. El borde común de proveedores ya existe; cada adapter oficial sigue condicionado a proveedor, credenciales, sandbox y contrato seleccionados.
6. Ya existen perfiles únicos componibles para backend y web y el sistema está listo para iniciar proyectos; no puede afirmarse que una configuración universal materializa proveedor, nube, mobile, analytics o IA sin decisiones del producto.
7. ~~El adapter Go no componía con PostgreSQL.~~ Cerrado en Go 0.2.1: tenant, hashes, campos outbox y migration de organizaciones/órdenes están alineados; build y repository integration pasaron contra PostgreSQL 18.6. Siguen condicionados roles, concurrencia y recovery.
8. ~~La configuración portable carecía de semántica ejecutable.~~ Cerrado para el ruleset común: validadores independientes Go/Python rechazan referencias, ciclos, permissions/capabilities y workflows inválidos. Cada producto aún debe fijar su validador estructural y extensiones legales.
9. ~~PostgreSQL nunca había sido ejecutado.~~ Cerrado para migración básica y restore lógico: `up-test-down-up-test` pasó en 18.6, compuso con Go y un dump real restauró con invariantes y cleanup. Siguen abiertos carreras multi-session, PITR, failover, volumen y roles mínimos.
10. ~~El adapter web no protegía rutas internas.~~ Cerrado: Authorization Code + PKCE/state/nonce, JWE `HttpOnly`, callback canónico, consultas server-only y journeys admin/customer/factory contra Go/PostgreSQL pasaron.
11. El prototipo `TS-ENTERPRISE-WEB` histórico mezcla health/migrations, DB/outbox y UI; queda `CANDIDATE` y fuera del perfil recomendado. Sus limitaciones no gobiernan el BFF vigente.
12. El backend vigente usa inbox/outbox/jobs con claim/lease y pruebas de retry/exhaustion. Un transport/proveedor real todavía debe demostrar idempotencia remota, backpressure, crash recovery y reconciliación.
13. Las APIs Go vigentes validan estado/versión, tenant, organización y subject; cantidades de PO, asignación multiunidad y carreras representativas siguen siendo extensiones/gates del producto.
14. El perfil BFF no declara un rate limit local como control productivo. El target debe seleccionar un edge confiable con proxy/header policy y antiabuso distribuido probado.
15. ~~La reconstrucción web vigente faltaba.~~ Cerrado y ampliado en V107: perfil autónomo 5 packs/69 archivos, Google SafeValues 1.2.0, CSP estricta nonce por request y Google CSP Evaluator 1.1.8, frozen offline, 21 tests, typecheck, build/licencia, Playwright Chromium desktop/móvil + Firefox/WebKit desktop runtime 4/4 y home+nonce 8/8, más Lighthouse cinco runs PASS; edge/CDN/WAF, Trusted Types/sinks/raw HTML, IdP/roles/backend, a11y AT, RUM/load, seguridad, deploy/rollback y producción siguen condicionados.
16. ~~No existía una vertical material de visitante→franquicia→cliente.~~ Cerrado parcialmente en V114: backend 17/135 y web 6/75 agregan ubicación pública, turno, operación de lead, quote server-priced, journey y entrega con PostgreSQL/browser/calidad reales.
